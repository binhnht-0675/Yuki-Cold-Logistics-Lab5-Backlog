# estimate-swp-report-ja

estimate-swp のレポートは表示がベトナム語固定（`<html lang="vi">`）で、言語の切り替えがない。
このスキルは**同じデータ**から日本語版を作り直し、数値が 1 つも変わっていないことを機械で確かめる。
翻訳ではなく再描画なので、数値・issue・親子関係は必ず原本の埋め込みデータ
（`<script id="report-data" type="application/json">`、`schemaVersion` 2.0 / `swp-matrix-v2` のみ対応）から取る。
描画は自作だが、派生する数値の式（不確かさの幅・構築／テスト／不具合の区分・チーム別・時間の換算率の既定値・
評価 A・B の「分かれた」判定・修正の SWP）は、原本スキルの関数をそのまま import して使う
（インストール済みの tkm:estimate-swp スキルの `scripts/core/` の `render_html.py`・`schema.py`・`render_assessor.py`。`scripts/ja_report_metrics.py`）。
スキルの場所は、環境変数 `ESTIMATE_SWP_SCRIPTS` → ホームの `.claude/skills/estimate-swp/scripts` → ホームの `.claude/skills/tkm/skills/estimate-swp/scripts`（キットの入れ直し後の配置）の順に探し、見つからなければ探した場所をすべて示して止まる（`scripts/ja_report_source_location.py`）。
原本スキルが入っていない環境では動かない（render・check とも exit 1）。

> **確認の範囲**: テストは架空のレポート（`../_shared/tests/fixtures/`）とその書き換え版（評価 B・分割の提案・分解が必要な親・
> `team:*` のラベル・既存の見積もり・空の実行を含む）。原本スキルの `validate_payload` に合格するのは基本の架空レポート
> （代表の修正を足した版）だけで、評価 B などを足した版は合格しない（その項目だけを除いて検査する）。
> 実データ（issue 399 件・親 101 件・処理レベル max）で render と check を実行し、全項目合格（2026-10-22・2026-10-23）。
> check の合格には、評価 B の根拠を含む英語・ベトナム語の記述すべての訳文（`--translations`）が要り、訳文には軸の表記を
> 書かない（下の「自由記述」の節）。
>
> **校正前のレポートは不合格**: `check` は `run.calibrationStatus` が `accepted` / `calibrated`（代表 issue のレビュー済み。
> `github-project-field-writer` が見積もりの書き込みに求める条件と同じ）でなければ不合格にする。提出版は校正を終えた原本から作る。
> `render` は校正の状態に関係なく日本語版を作る（レビュー中の確認用）。

## 日本語版に出す表
原本スキルの `references/html-report.md`（Required content 1〜9）に合わせる。数値にはすべて照合用の印を付ける。
- 対象の範囲（`run.selection` があるとき）: クローズ済み・既存の見積もりの扱い、状態の判定、絞り込み、除外の件数
- 要約: SWP 合計・オープン / クローズ・親の数、不確かさの幅と求め方（確信度「高」は点数のまま、「中」「低」は有効な SWP の
  並びでひと段階下げた合計〜上げた合計）、合計に含まない「分解が必要」の親、分割の提案と確信度「低」の件数と SWP、
  数値のタイル、評価 A・B の一致（一致 / 軽微な差 / 大きな差 / 区分違い）、計画と不具合・手戻りの構成と区分ごとの小計、
  作業種別ごとの小計、SWP の分布（表と棒。JavaScript 不要）、既存の見積もりとの比較（差があるとき）
- 算定方法（難易度の五段階、時間は参考値。本文に Scope・Complexity は出さない）と、折りたたみの「技術的な詳細」
  （`<details id="tech-details">`。範囲と複雑さの段階・係数・有効な値を説明するが、issue ごとの値と「S × C」の表記は出さない）
- **Scope × Complexity は表示しない**（原本スキルの契約: 軸の値と S×C の表記は埋め込みデータだけに置く）。issue 一覧・代表 issue の
  表は SWP だけを出し、軸の値は埋め込みデータ（`check` で原本と照合）と照合表の代表 issue 表にだけある
- チーム別の負荷（`team:*` のラベルがあるときだけ）、リスクと対応（分割の提案・確信度「低」・分解が必要な親。対応の文は
  固定文＋記録された理由〈splitReason / 最初の不明点 / 根拠〉の訳）、時間への換算（参考値。換算率は読む人が変え、保存しない）
- issue 一覧: 親ごとのまとまり（件数・小計）、SWP、タイトルと印（分割提案・クローズ・評価が分かれた・A · B の差）、
  分野、作業種別、確信度（軸の列はない。点数が校正で変わった issue は詳細に初期 → 校正後の SWP を出す）。
  詳細: 点数（変わったときだけ初期 → 校正後）と難易度、根拠、前提、不明点、分割の理由、機能・作業、取得元、評価 B の SWP と根拠
- 親の集計: 種別、集計、子、子の数、初期 SWP、SWP
- 校正: 冒頭の説明、代表 issue（SWP・issue・タイトル・難易度・選定理由・スキルの評価（初期 SWP）・**担当者の確定（SWP）**・**調整の理由**）、
  担当者の修正（初期 → 確定の SWP、この issue だけ / 似た issue にも適用、理由）、適用したルール（分野・作業種別ごとの段の移動）。
  担当者の確定の有無は `corrections[]`（なければ issue の `calibration.approvedScope / approvedComplexity`）で決め、表には確定後の SWP を出す。
  理由は `corrections[].rationale`。適用したルールの段の移動は「範囲 +1 段、複雑さ 0 段」のように書く（契約 6 の帯の段）。
  埋め込みデータにない場合は「—」と表示し、照合表の代表 issue 表にも「—（埋め込みデータに理由なし）」と書く。
- 注意事項: 埋め込みデータの注意、処理レベル「低」の固定文、評価 A・B の固定文（一致は検証済みではない）と
  人が見ていない「分かれた」issue の件数（評価 B を実施できなかったときはその理由）
- 埋め込みデータ（`<script id="report-data" type="application/json">`）: 原本の埋め込みデータと同じ構造の全項目。
  変えるのは自由記述（下の「自由記述」の節の欄）を日本語にすることと、`run.sourceLabel` を出典欄と同じ固定の文にすることだけ。
  issue の本文（`body`）は入れない。エスケープは原本スキルと同じ（`<` `>` `&` U+2028 U+2029）。別に `report-data-ja` に
  原本のファイル名と sha256・データの sha256・省略 / 置換の件数を入れる
- 検索・絞り込み（分野・作業種別・確信度・校正）と SWP の数値での並べ替え。表示用の固定スクリプト 1 つだけで、ない環境でも全行が読める
  （ネットワーク・eval・innerHTML・イベント属性・保存なし。文字は textContent で書く）

## コマンド
スクリプト: `scripts/render-estimate-report-ja.py`

1. 日本語版を作る
   ```
   python3 scripts/render-estimate-report-ja.py render --html <原本.html> --out reports/<名前>-ja.html \
     [--verification-md reports/<照合表>.md] [--repo owner/name]
   ```
   - 注意事項の「照合表（…）」には `--verification-md` のファイル名を書く（省略時は `estimate-swp-verification-ja.md`）。
     check にも同じ `--verification-md` を渡す。名前が違えば check の「照合表の名前」が不合格になる。
   - 既存ファイルは上書きしない（`--force` で上書き）。`--out` に原本と同じパスは指定できない。
   - 書き出す前に、読み手に見える文字列（本文・リンク先・埋め込みデータ）を `../_shared/content_guard.py` で検査する
     （ベトナム語・制御文字・内部パス・秘密情報・メール・公開しない用語・社内 URL / 社名・`--repo` 以外のリポジトリの
     GitHub URL）。1 件でも当たれば書き出さずに exit 3。該当する自由記述は `--translations` で置き換える。
     `--repo` を省略したときは、`issueRef` のリポジトリが 1 つならそれを許す。
   - 出典欄に `run.sourceLabel` は出さない（組織名・非公開の Project 名を含みうるため）。固定の文
     「estimate-swp の評価結果（対象の名前は公開版に載せない。原本 HTML の sha256 で照合）」を出し、埋め込みデータの
     `run.sourceLabel` も同じ固定の文にする（表示専用の名前で、`validate_payload` は空でない文字列であることだけを求める）。
     `run.sourceUrl` はそのまま入れ、内容検査を通す（`--repo` の持ち主の `github.com/users|orgs/<owner>/projects/N` だけを許す）。
   - 内容検査は、埋め込みデータを JSON として読み、文字列（キーを含む）を 1 行ずつ検査する。
   - 外部読み込みなし。スクリプトは表示用の固定のもの（`scripts/ja_report_interaction.py` の `SCRIPT`）だけ。表示する数値には照合用の印（`data-v`）、自由記述には `data-t`、
     出所欄（原本のファイル名・sha256 の先頭・照合表の名前）には `data-x` を付ける。
2. 検査して照合表を作る
   ```
   python3 scripts/render-estimate-report-ja.py check --html <原本.html> --ja reports/<名前>-ja.html \
     --verification-md reports/estimate-swp-verification-ja.md --source-skill "tkm:estimate-swp <版>" [--repo owner/name]
   ```
   検査項目（1 つでも不合格なら exit 1）:
   - `<html lang="ja">` である
   - ベトナム語の文字（声調記号付きの母音とストローク付きの d。合成済み・分解済み〈NFD〉のどちらも数える）が 0
   - `data-v` の印が付いた数値すべてが、原本の埋め込みデータから再計算した値と一致
   - 表示される本文（タグ・属性・`<style>`・`<script>` を除く）で、印のない数値が 0。例外は次のものだけ: 固定文（算定方法の難易度の目安、語「sha256」）、
     埋め込みデータの文字列か訳文と完全一致する自由記述（`data-t`）、出所欄（`data-x`、原本と照合）
   - 網羅: すべての表の数値の欄（全 issue の SWP、代表の初期 SWP と確定 SWP、全親の SWP と子の数、
     合計・確信度別・分割の提案・分解が必要な親・修正数・ルール数、作業種別、代表、親ごとの件数、注意事項の件数）が表示されている。
     必要なキーは、埋め込みデータから決めた一覧と、埋め込みデータから描き直した版の `data-v` の全キーの和
   - 印の並び: 日本語版の印（`data-v` のキーと数値、`data-t` の文、`data-x` の出所）の順番と中身が、同じ訳文で
     埋め込みデータから描き直した版と完全に一致する（数値の欄を `data-t` の文に置き換える・欄を消す・欄を足す、はすべて不合格）
   - 訳文（`--translations` を渡したとき）: 原文が埋め込みデータの文字列であり、訳文の数値（NFKC 後の算用数字）が
     原文の数値と同じ（順番は問わない）。ただし原文の軸の表記（「S5 × C3」など、`scripts/ja_report_axis_guard.py` の
     `AXIS_NOTATION_RX`）は、その数字ごと訳文から外してよい（ほかの数字を落とす・足すのは不合格）
   - 訳のない自由記述 0: 日本語でない記述（ベトナム語の文字がある、または日本語の文字がなく英字の語が空白をはさんで続く）で
     訳文のないものを、省略の文に置き換えた箇所が 0（1 か所でもあれば不合格。評価 B の根拠も対象）。表示と埋め込みデータの件数を別々に出す
   - 表示部に Scope × Complexity がない: `<script>`・`<style>`・折りたたみの「技術的な詳細」を除いた部分に、軸の欄
     （`data-v` のキーが …scope / …complexity。適用したルールの段 `rule|n|scope` などは除く）がなく、固定文に「Scope」
     「Complexity」「×」がなく、自由記述（`data-t`）に軸の表記（「S5 × C3」「S×C」「Scope × Complexity」「Scope を 2」
     「複雑さが C3」、単独の「S5」「C3」、数字が単独で句読点か末尾が続く「Scope: 3」「スコープ 3」「複雑度 2」「範囲 3」「複雑さ 2」など。
     NFKC 後に照合するので全角の「Ｓ５ × Ｃ３」も対象。段階の語が付く「難易度は水準2」「範囲はレベル3」、括弧が続くか括弧で囲む
     「範囲8（42表）」「Scope（3）」も対象。
     「範囲:3 セクション」のような件数、「複雑さ：1,000 行」「239/240/241 分」のように区切りの後に数字が続く値、
     製品名「Amazon S3」「S3 バケット」は対象外）がない。ベトナム語で書かれた担当者の理由の軸の値（「範囲」「難易度」に
     当たる語の直後の単独の数字、または「水準 N」。声調記号のない書き方も含む）も軸の表記として扱い、訳文で省いてよい（その他の数字は省けない）
   - 内容検査: 日本語版の本文・リンク先・埋め込みデータに、公開リポジトリに出せない内容がない（render と同じ規則）
   - 親の SWP = 子の SWP の合計（集計 `derived` の親だけ。`needs-breakdown` などほかの親は検査しない）。
     子が埋め込みデータにない、または子の SWP が空なら不合格（0 として数えない）。代表の担当者確定 = 最終の Scope × Complexity
   - 出所: 日本語版に記録した原本 HTML の sha256 と、埋め込みデータの sha256 が一致
   - スクリプトは JSON のデータと表示用の固定スクリプト（文字列が完全一致）だけ。外部読み込み・イベント属性がない（リンクは `https://github.com/` で始まるものだけ。render は issue の URL だけを出す）
   - 日本語版に表示する列挙値すべて（分野・作業種別・確信度・根拠の種類・issue の校正・代表の選定理由・処理レベル・
     レポートの校正・親の種別・親の集計・作業・取得元・取得状況・取得した項目・評価の一致・評価 B を実施できない理由・
     状態の判定・既存の見積もりの確認・除外・見積もりの出所・ルールの分野と作業種別）が `references/label-map-ja.json` か
     `scripts/ja_report_text.py` の `EXTRA_LABELS` にある（未登録の値は原文のまま表示されるので不合格）。
     表示しない `state` は対象外
   - 埋め込みデータ（5 項目。表から外した軸の値はここで照合する）: (1) 原本スキルの `validate_payload`
     （`tkm:estimate-swp スキルの scripts/core/schema.py`）に合格、(2) 置き換えた欄（自由記述と `run.sourceLabel`）と
     `body` を除いた全項目が原本の埋め込みデータと完全一致（Scope・Complexity・列挙値・署名を含む）、(3) 置き換えた欄が
     同じ訳文で決まる文と完全一致、(4) issue と親の件数・識別子が表示した行（`issue|…|final`・`parent|…|final`）と一致、
     (5) JSON に未エスケープの `<` `>` `&` U+2028 U+2029・`body`・ベトナム語の文字がない
   - 校正済み: `run.calibrationStatus` が `accepted` / `calibrated`（`pending`・`skipped`・空は不合格）
   照合表には上記の結果、検査範囲の説明、代表 issue 表、原本と日本語版の sha256、原本を作ったスキルの版、
   本スキルの版、実行コマンドを書く。数値の照合表の左列は「埋め込みデータから再計算」した値。
   照合表も書き出す前に内容検査を通す。当たれば照合表は書き出さず、不合格（exit 1）。
   実行コマンド欄では、ファイルを指す引数（`--html` `--ja` `--out` `--verification-md` `--translations` と絶対パス）を
   すべてファイル名だけにする（作業フォルダの構成がわかる相対パスやローカルのユーザー名を出さない）。

## 自由記述（根拠・前提・不明点・注意事項・調整の理由）の扱い
estimate-swp の根拠などは評価したエージェントの言語（多くはベトナム語）で書かれている。表示と埋め込みデータの両方で、
次の欄を同じ規則で日本語にする（`scripts/ja_report_payload.py` の `FREE_TEXT_FIELDS`）: issue のタイトル・根拠・前提・不明点・
分割の理由・裏付け（`supportingEvidence`）・取得元の注記（`provenance.notes`）・評価 B の根拠、親のタイトル・取得元の注記、
担当者の修正の理由、注意事項。列挙値・署名・ラベル・状態・ルール ID などの識別子は訳さない。順番に:
1. `--translations` の JSON（`{"原文": "日本語訳"}`）に完全一致する原文があれば、その訳を使う。
2. 日本語でない記述でなければ（日本語の文字がある、または英字の語が空白をはさんで続かない。例: 識別子・ラベル）原文のまま使う。
3. それ以外は「（原文がベトナム語のため省略。原本 HTML を参照）」または「（訳文がないため省略。原本 HTML を参照）」と表示し、
   件数を注意事項に書く。**check はこの件数が 1 以上なら不合格**（訳のない文をそのまま出すことも、黙って省くこともしない）。
   チームのラベル（`team:*`）と絞り込みの値は識別子なので訳さず原文のまま出す（ベトナム語の文字があれば check の別項目で不合格）。
訳を使ったときは `check` にも同じ `--translations` を渡す（訳文を照合するため）。
訳文にベトナム語の文字がある → render・check とも exit 2（check は検査の前に止まる）。原文が埋め込みデータにない・訳文の数値が
原文の数値と違う → render は exit 2、check は不合格（exit 1）
（原文が数を語で書いていれば〈「一つ・二つ」にあたる語〉、訳文も「ひとつ・ふたつ」のように語で書く。数字を足さない）。
数値・列挙値は訳の対象外で、必ず埋め込みデータとラベル表から出す。
訳文に軸の表記（「S5 × C3」「Scope を 2」など）を書かない（表示部の検査で不合格になる）。原文にあれば、その表記を数字ごと外して訳す。

## 提出物の置き方
- 原本 HTML（ベトナム語表示）は公開・提出するリポジトリに置かない。非公開の場所（例: `.gitignore` 済みの
  `private/` フォルダ）に保管し、照合表の sha256 でたどれるようにする。
- 提出するのは日本語版 HTML と照合表だけ。両方を同じ `reports/` に置く。
- 照合表のコマンド欄ではファイルの引数をファイル名に縮める（ローカルのユーザー名・作業フォルダの構成を出さないため）。

## 終了コード
| コード | 意味 |
|---|---|
| 0 | 正常（check は全項目合格） |
| 1 | check の不合格（校正前のレポートを含む）、照合表が内容検査に当たった、埋め込みデータの読み込みエラー |
| 2 | 引数の誤り、訳文の誤り（render: ベトナム語・埋め込みデータにない原文・数値の違い。check: 訳文のベトナム語） |
| 3 | render が内容検査で停止（日本語版 HTML は書き出していない） |

読む項目の一覧は `references/payload-fields.md`。
